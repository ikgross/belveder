# Изменение движка

## Принципы

- Всё в engine — чистые функции: `step(state, action, world) -> state`. Действия: `choose`, `continue` (уйти с экрана последствия), `pledge` (заложить воспоминание), `newNight`. Ни одной мутации входа, ни одного побочного эффекта.
- Фазы состояния: `scene` → (`outcome` →) `scene` … → `report` или `ending`. Эффекты выбора применяются до фазы `outcome`; после неё: `ending` → конец игры (`endings.<id> = 1`, отчёт, история, фаза `ending`), `endNight` → отчёт, иначе первый подходящий `interrupts[].goto`, иначе `goto` выбора. Ночь заканчивается только `endNight`, залогом воспоминания или концовкой. На каждом конце ночи в `state.history` добавляется запись для рассказа (`NightRecord`), профиль несёт её между ночами.
- Рандом только через `rng.ts` (mulberry32): состояние RNG лежит в `state.rng`, каждое использование возвращает новое значение. Одинаковый seed + одинаковые действия = одинаковое состояние, байт в байт.
- Движок не знает о мире: имена качеств, локаций, сторилетов приходят из `world`. Глобальные правила (`onChoice`, `interrupts`, `onNightEnd`) — тоже данные из `world.rules`. Единственные id, которые движок пишет сам, — `RESERVED_QUALITIES` из content-schema (`pledged.<id>`, `returned.<id>`, `returned_tonight`, `memories_returned`, `found.<id>` для улик, `endings.<id>` и `ending_night` для концовок): это имена механики, а не мира, и validator требует их объявления.
- Нет `Date`, `Math.random`, `console`, `fetch`, `window`.
- Всё, что нужно экрану, — чистые «view»-функции от состояния: `currentScene`, `currentOutcome`, `currentReport`, `currentNotes`, `pledgeOptions`, `choiceCost`, `changedQualities`, `notebookView`, `evidenceView`, `clockTime`, `isTense`, `endingView`, `storyView`; `newCase` даёт профиль следующего дела. Память интерфейса (какая подсказка уже показана, какая страница прочитана, какая улика открыта) живёт в приложении, не в `GameState`.

## Тесты

Главный вид тестов — сценарные прогоны:

- `packages/engine/test/night.test.ts` — мини-мир внутри теста (`test/mini-world.ts`), проверяет сам движок.
- `packages/validator/test/belvedere-night.test.ts` — реальный `content/belvedere`, проверяет мир.

1. Сценарий = seed + список индексов выборов + мир.
2. Прогон даёт финальный state (включая лог). Digest = sha256 от канонической сериализации (ключи отсортированы, см. `engine/digest.ts`).
3. Ожидаемый digest и снимок лежат в `test/golden/<name>.json` рядом с тестом; helper `packages/engine/test/golden-helper.ts`. Тест сначала показывает diff снимка, потом падает по хешу.

Мелкие юнит-тесты пишем только для нетривиальных функций (парсер условий, кодек storage).

## Когда digest меняется

Digest обязан измениться только если изменилось **поведение**. Порядок действий:

1. Убедись, что изменение поведения намеренное. Если нет — это баг, чини.
2. Запусти `bun test` и посмотри, какие сценарии упали. Проверь diff лога, а не только хеш: `UPDATE_GOLDEN=1 bun test` перезапишет golden-файлы, `git diff test/golden` покажет, что именно поменялось.
3. Объясни в `docs/golden-changelog.md`: одна строка на каждый изменённый golden (`дата · тема коммита · golden · почему`), в том же коммите. Тема, а не хеш: хеш до коммита неизвестен, а amend его меняет. Сообщение коммита остаётся однострочным. Обновлённый golden без строки в changelog — ошибка ревью.
4. Изменение контента тоже может менять digest сценариев на реальном мире — это нормально, но строка в changelog всё равно нужна.

## Чек-лист

- [ ] Новый рандом идёт через `rng`?
- [ ] Схема состояния поменялась → поднял `STATE_VERSION` в `engine/state.ts`, формат сохранения → `STORAGE_VERSION` в `engine/storage.ts`, и добавил миграцию или сброс?
- [ ] Добавил или расширил сценарный тест?
- [ ] Golden обновлён осознанно, и в `docs/golden-changelog.md` есть строка на каждый изменённый файл?
